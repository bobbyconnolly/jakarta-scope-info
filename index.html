Understanding Jakarta EE Scopes

In Jakarta EE (formerly Java EE), scope refers to the lifecycle and visibility of objects within your application. Understanding scopes is crucial for proper data management and sharing information between different parts of your web application.

Let's explore the three most common scopes you'll encounter in Jakarta EE applications:

Note: There are other scopes in Jakarta EE (like page scope in JSP), but we'll focus on these three primary scopes for clarity.

R

Request Scope

The Ephemeral Scope

Request scope is the most short-lived scope in Jakarta EE applications. Objects in request scope exist only for the duration of a single HTTP request-response cycle.

What does "ephemeral" mean? The word ephemeral means "lasting for a very short time." In web applications, request-scoped objects are ephemeral because they have the shortest possible lifespan - they're created when a request arrives, used during processing, and then immediately discarded when the response is sent back to the browser.

Why is it so ephemeral?

  • Created when the HTTP request arrives at the server
  • Destroyed immediately after the response is sent back to the client
  • Each new request creates a completely new set of request-scoped objects
  • No data persists between requests, even from the same user

When to use Request Scope:

  • Form submissions
  • Request parameters
  • One-time calculations needed only for the current request
  • Temporary data that shouldn't persist beyond the current operation

Code Example:

// In a servlet - setting a request attribute
HttpServletRequest request = ...;
request.setAttribute("temporaryData", calculatedValue);

// Accessing the attribute in the same request processing
String value = (String) request.getAttribute("temporaryData");

// IMPORTANT: In a completely new HTTP request, this data is GONE
// Each HTTP request gets its own fresh request scope

Important Note on Request Scope Lifecycle

The request scope is tied to a single HTTP request processing cycle. This means:

  • When a browser makes an HTTP request to your server, a new request object is created
  • Any attributes you set are only available during that single request's processing
  • Once the response is sent back to the browser, all request attributes are discarded
  • If the user clicks another link or submits another form, it creates a completely new request with a fresh, empty request scope

Think of the request scope as a temporary notepad that gets thrown away immediately after you finish using it.

S

Session Scope

Session scope persists data for a specific user across multiple requests. Objects in session scope are associated with a unique user session.

Key characteristics:

  • Created when a user first accesses the application
  • Persists across multiple requests from the same user
  • Destroyed when the session times out or is explicitly invalidated
  • Data is user-specific and not shared between different users

When to use Session Scope:

  • User login information
  • Shopping carts
  • User preferences
  • Step-by-step wizards where state needs to be maintained

Code Example:

// In a servlet - storing data in session
HttpServletRequest request = ...;
HttpSession session = request.getSession();
session.setAttribute("userCart", shoppingCart);

// In another servlet - retrieving data from session
// (Works across multiple requests from the same user)
HttpSession session = request.getSession();
ShoppingCart cart = (ShoppingCart) session.getAttribute("userCart");
A

Application Scope

Application scope has the longest lifecycle and is shared across the entire application. Objects in application scope are accessible to all users and all requests.

Key characteristics:

  • Created when the web server starts up or when your application is deployed
  • Persists until the application is undeployed or the server shuts down
  • Shared across all users and all requests
  • Must be thread-safe as multiple users may access simultaneously (explained below)

Application Scope and Server Architecture

It's important to understand that "application scope" means "for as long as the server is running." This has significant implications:

  • Traditional servers: Run continuously and maintain application-scoped objects indefinitely
  • Serverless environments: May spin up and down, potentially losing application scope data
  • "Stateless" design: Modern architectures often avoid storing critical data in application scope to:
    • Make scaling easier (can add more server instances)
    • Reduce bugs caused by shared state
    • Improve developer velocity (easier to reason about code)
    • Enable zero-downtime deployments

When using application scope, consider whether the data would be better stored in an external database or cache, especially if your application needs to scale horizontally across multiple servers.

When to use Application Scope:

  • Application configuration
  • Shared resources
  • Cached data
  • Connection pools
  • Global counters

Code Example:

// In a servlet or context listener - storing app-wide data
ServletContext context = getServletContext();
context.setAttribute("productCatalog", catalog);

// In another servlet - accessing app-wide data
// (Works for all users, all requests, throughout the application)
ServletContext context = getServletContext();
ProductCatalog catalog = (ProductCatalog) context.getAttribute("productCatalog");

Thread Safety in Application Scope

When using application scope, thread safety becomes a critical concern. Let's understand why:

What is thread safety?

Thread safety means your code will function correctly when accessed by multiple threads (users) at the same time. Without proper thread safety, strange behaviors, data corruption, or incorrect results can occur.

Why is application scope particularly vulnerable?

Application-scoped objects are shared among all users of your application. This means:

  • User A and User B might both access the same object simultaneously
  • If User A is modifying data while User B is reading it, User B might get inconsistent data
  • Multiple threads might try to update the same variable at the same time

Example of thread safety issue:

// NOT thread-safe (in application scope)
public class Counter {
    private int count = 0;
    
    public void increment() {
        count++; // This is not an atomic operation!
    }
    
    public int getCount() {
        return count;
    }
}

// Thread-safe version
public class SafeCounter {
    private AtomicInteger count = new AtomicInteger(0);
    
    public void increment() {
        count.incrementAndGet(); // Atomic operation
    }
    
    public int getCount() {
        return count.get();
    }
}

In the unsafe example, if two users increment at the same time, the value might only increment once instead of twice! This happens because count++ isn't a single operation - it reads, increments, and then stores.

Choosing the Right Scope

When deciding which scope to use for your objects, consider these questions:

  • How long should the data live? Use the most restrictive scope possible.
  • Who needs access to the data? A single request, a specific user, or everyone?
  • What's the memory impact? Application-scoped objects live longest.
  • Is thread safety a concern? Application-scoped objects need thread-safe implementations.

Understanding Scope Relationships

It's helpful to understand how the different scopes relate to each other. You can think of Jakarta EE scopes as nested containers:

Application Scope (All users, entire server)
Session Scope A (User 1)
Request 1
Request 2
Session Scope B (User 2)
Request 1

Key points about scope relationships:

  • A single application can have many session scopes (one per user)
  • Each session can have many request scopes (one per HTTP request)
  • Objects in larger scopes are visible to smaller scopes (but not vice versa)
  • Smaller scopes can read from but not write to larger scopes (without special methods)

This nesting helps you understand the relationship between different scopes and why objects in application scope are accessible to all sessions and requests, while request-scoped objects are isolated to just one HTTP request.

Common Pitfalls When Working With Scopes

Common Mistakes to Avoid

1. Using the wrong scope for your data

Mistake: Storing user-specific data in application scope.

Problem: All users will see the same data, leading to information leaks and security issues.

Solution: Store user-specific data in session scope instead.

2. Assuming request data persists between requests

Mistake: Setting a value in request scope and expecting to access it in a future request.

Problem: The data will be gone as soon as the response is sent.

Solution: Use session scope for data that needs to persist across multiple requests.

3. Creating memory leaks in session scope

Mistake: Continuously adding data to session scope without ever cleaning it up.

Problem: Session memory grows larger and larger, potentially causing server performance issues.

Solution: Remove data from session when no longer needed, or use request scope for temporary data.

4. Not handling thread safety in application scope

Mistake: Using non-thread-safe objects or collections in application scope.

Problem: Concurrent access can corrupt data or cause unpredictable behavior.

Solution: Use thread-safe collections (ConcurrentHashMap, etc.) and synchronize access to shared resources.

5. Storing too much data in session

Mistake: Putting large objects or too many objects in session scope.

Problem: High memory usage, especially with many concurrent users.

Solution: Store only necessary data in session, consider databases for larger datasets.

6. Initializing shared resources in servlet-level scope

Mistake: Creating resources in servlet's init() method when they need to be accessed by other servlets.

Problem: Other servlets can't access resources initialized within a single servlet. 

@WebServlet("/inventory")
public class InventoryServlet extends HttpServlet {
    
    private static final long serialVersionUID = 1L;
    private InventoryManager manager;  // ← PROBLEM: Only available in this servlet!
    
    @Override
    public void init() throws ServletException {
        // Initialize the inventory manager with sample data
        manager = new InventoryManager();
    }
    
    @Override
    protected void doGet(HttpServletRequest request, HttpServletResponse response) 
            throws ServletException, IOException {
        // Using manager here works fine
        // ...
    }
}

Problem scenario: If you want to create another servlet, e.g., CategoryServlet, that needs to modify the same inventory data, it cannot access the manager instance because it's scoped to the InventoryServlet class.

Solution: Move shared resources to application scope in a context listener or use application-scoped beans: 

@WebListener
public class AppContextListener implements ServletContextListener {
    
    @Override
    public void contextInitialized(ServletContextEvent sce) {
        // Initialize the inventory manager with sample data
        InventoryManager manager = new InventoryManager();
        
        // Store in application scope
        sce.getServletContext().setAttribute("inventoryManager", manager);
    }
}

@WebServlet("/inventory")
public class InventoryServlet extends HttpServlet {
    
    @Override
    protected void doGet(HttpServletRequest request, HttpServletResponse response) 
            throws ServletException, IOException {
        // Get manager from application scope
        InventoryManager manager = 
            (InventoryManager) getServletContext().getAttribute("inventoryManager");
            
        // Use manager...
    }
}

@WebServlet("/category")
public class CategoryServlet extends HttpServlet {
    
    @Override
    protected void doPost(HttpServletRequest request, HttpServletResponse response) 
            throws ServletException, IOException {
        // Get the SAME manager instance from application scope
        InventoryManager manager = 
            (InventoryManager) getServletContext().getAttribute("inventoryManager");
            
        // Now both servlets can work with the same object
        String newCategory = request.getParameter("category");
        manager.addCategory(newCategory);
        // ...
    }
}

Remember that request scope is highly ephemeral but provides a clean slate for each request, minimizing the chance of data leakage between different operations. Always default to request scope unless you specifically need the data to persist longer.
